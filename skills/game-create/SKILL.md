# 新游戏创建

把游戏想法整理成可执行的详细需求，保存到正在承接它的任务。用户只要策划时交付方案；用户已要求制作游戏时，写好方案后继续开发，不把规划变成额外审批环节。

## 先读取当前项目

读取会话根的 `workspace.json`、`context/current.json` 及其指向的 manifest，确认项目、分支、session、run、执行模式和用户已有决定。通过 `world_read`、`semantic_read` 查看真实场景/预制件目录，用 `knowledge_search` / `knowledge_read` 读取相关设计；只按需查看关联源码。已有内容要复用，不因“新项目”字样清空当前工程或另建服务。

需求存在会改变玩法、资产选型或开发规模的关键歧义时，集中询问少量问题，并继续不依赖答案的工作。可推断的小项明确记录假设，不能把假设写成用户已确认。规划模式遵从当前只读限制，不调用写入、导入、构建或发布工具。

## 1. 拆分需求与内容职责

从核心体验拆出玩家行为、游戏规则、场景内容、表现与 UI，给需求分配可追踪的编号。建立两张简洁清单：

- **场景**：名称/拟定路径、用途、进入/退出条件、承载的规则与内容、依赖的预制件。数量由实际流程决定，说明为何独立；不要默认每款游戏都有大厅、多个关卡或单独结算场景。
- **预制件**：名称、职责、使用场景、组合/依赖关系、复用或新增理由、需要独立调整的属性。可反复摆放/生成、有变体、需要独立编辑的角色、敌人、道具、机关、UI、效果适合拆分；一次性小细节留在所属场景。无模型的逻辑系统也要有清楚的归属，不把每个脚本或几何体都拆成预制件。

原生预制件应是可独立打开的真实 PackedScene，包含稳定的可编辑子节点。区分定义、场景中的实例与纯素材；变体优先继承/组合或共享配置。具体原生约束见会话 `WORLD-API.md` 的 “Prefab authoring and structure”。这里只规划职责，不把目录卡片或空壳当作已实现产物。

## 2. 定义玩法框架

逐项作出符合用户意图的选择，记录理由与未决项：

- 2D / 3D（需要混合时说明哪层），镜头、输入方式、目标平台与 Web 使用要求。
- 核心循环：玩家做什么、获得什么反馈、如何推进；胜负/完成条件、难度与重玩方式。
- 是否有主角；有则说明控制对象、移动/交互/战斗和相机，无则明确棋盘、卡牌、经营等操作主体，不自动加入人形角色。
- 单人、同屏多人或联网多人；人数、合作/对抗、加入退出、输入归属、状态与存档责任。**协作编辑和多个独立 Play 窗口不代表多人玩法。** 对联网需求核对当前执行环境支持的权威运行契约；未支持的部分保留为需求与缺口，不擅自降级成单人，也不将原生内容送入旧 JSON 权威入口。
- 场景流转：入口 → 主要玩法 → 完成/失败 → 重开/返回，按实际游戏删减或扩展；标明触发条件、传递状态、哪些数据重置、哪些跨场景保留。可以用紧凑流程表，不强制引入图表工具。

编辑 Play、新页 Web、导出和技术测试共用登记的 canonical 工程、`GameRuntime` 与 `standalone.tscn`；按当前 `WORLD-API.md` 规划真实场景跳转。游戏自己的持久状态要明确归属，不能假设上个场景节点仍存活。

## 3. 搜集素材并定义可检索描述

先查项目已用素材与市场：`asset_catalog` → `asset_search` → 按需 `asset_detail`。准备外部美术、音效、音乐、UI 或字体时，读取同级 [game-assets](../game-assets/SKILL.md)，按需要实际搜索并记录候选。每类当前必需素材至少有可用候选或明确的搜集缺口；搜索词本身不能冒充已找到资源。这里只要求准备到可继续获取的程度，不强制提前下载全部候选。

每条素材需求写清：

- 对应场景/预制件/UI 状态及用途；画风、轮廓、配色、主题，中文/英文搜索词。
- 2D/3D 格式、尺寸/比例、分辨率；动画、骨骼、拆件、碰撞或挂点需求，按实际类型填写。
- 音效的触发动作、情绪、时长、循环/衔接；音乐的氛围与循环；UI 的控件状态、字号/中文覆盖、九宫格或透明要求。
- 已选/候选资源的真实页面、作者、许可与署名要求、固定版本/文件标识；可用性、适配工作和缺失项。未检索、已找到、已下载、已导入分别标记。

有适合的现有角色就复用；需要可操控人形主角且未指定外观时按 `game-assets` 的官方角色流程选取。坦克、棋盘等玩法不添加无关人形角色。素材字节留在工作区，需求文档只记录引用和规格。需要下载/制作时再按资产技能执行，遵从当前模式与授权。

## 4. 写详细需求并记录当前任务

使用 [需求文档结构](references/requirements.md)，删去不适用项，填入前面实际得出的结论。每项玩法需求应能追踪到场景/预制件、素材和可观察的完成条件；标明用户确定、合理假设和等待决策，避免只有空表或泛泛愿景。

**当前任务对话是必需记录。** 在当前任务回复中提交完整的详细需求正文，包含项目/分支、输入源版本和实际 session/run 标识（以 context 为准，不编造 task ID）。允许写文件时，再保存到会话根 `outputs/tasks/<run_id>/requirements.md`，在回复中给出真实路径；持续同一任务则保留修订记录。规划模式不允许落盘时，直接在任务对话交付完整正文，并说明未写文件。

共享知识是另一份有明确可见范围的设计摘要。执行模式允许、且已开始落实共享设计时，先读现有条目，再按 `SEMANTIC-AUTHORING.md` 使用 `knowledge_write` 保存公共玩法/结构决定，区分“计划”与“已实现”。不要复制私人对话、整份任务历史或临时测试结论；不为写知识调用不存在的 task_write 工具，也不直接修改任务数据库。

如已获开发授权，接着使用 [game-change](../game-change/SKILL.md) 的实施与交付流程，将本方案作为输入。保存源码、完成构建、实际游玩、显式发布分别记录；不添加自动验收 Agent 或发布动作。
