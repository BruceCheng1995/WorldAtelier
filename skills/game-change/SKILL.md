# 游戏需求修改与交付

让用户需求沿着真实的场景、预制件和代码关系落地，并留下可复用的说明与实际测试结果。改动规模由需求决定；小改动保持简短，不强制全工程重构或全量测试。

## 1. 统计关联并确定修改范围

先读会话 `workspace.json`、`context/current.json` 及当前 manifest、`WORLD-API.md`、`SEMANTIC-AUTHORING.md`。从用户原话和已记录的需求中提取这次的目标与不变条件，再查：

1. `semantic_read` 的现有场景/预制件目录、描述、关联及真实属性；`knowledge_search` / `knowledge_read` 的相关设计决定。
2. `world_read` 的当前源版本和相关资源/文件，继而按实际路径搜索引用、调用者、实例、生成点、信号和数据配置。知识和描述可能过期，以当前原生源事实校正，不能只按相似名称选对象。
3. 用户对象/空间/试玩附件的捕获版本、场景身份和完整实例地址。附件与当前源有差异时确认对应关系，运行生成对象不能凭名称猜成源节点。

写一份精简影响表：**需求 → 相关场景/预制件/代码（真实 ID、路径）→ 关联原因 → 修改/复用/新增 → 受影响实例与回归范围**。说明新增的必要性；没有复用空间才新增独立定义。定义默认值、单实例覆盖、场景布局与游戏级规则要分清：例如“只把门口这只敌人变慢”应定位实例，“所有同类敌人变慢”才修改定义默认值。保留已存在的显式实例覆盖。

需求冲突或缺少决定性输入时询问用户，同时继续无依赖的分析。普通可逆编辑已有授权就继续，不用整份方案审批取代执行。纯方案/规划模式只给影响分析与实施计划，遵从只读限制，不调用共享写入或开始开发。

## 2. 指定验证方案

在修改前说明如何证明用户要的行为，规模与改动相称。采用“前置条件/固定输入 → 操作 → 可观察的期望结果 → 需要保留的证据”，同时覆盖相关旧行为。例如修改预制件默认速度，要检查实际移动以及具有显式覆盖的实例仍保持自己的值。

当行为复杂、存在回归风险或需复现时，准备可执行断言、测试脚本或验收描述；简单文案/参数修改可用读回与针对性操作验证，不为每个改动新增测试框架。区分源码/导入、canonical 启动、实际交互、画面/音频、目标 Web 和多人同步的证据。仅 headless 启动不能证明视觉、听感或多人玩法。

记录计划采用与本次不适用的检查。Agent 自己选择测试，不创建平台自动检查任务、独立验收 Agent 或保存前审批门禁；测试失败是需要修复/报告的事实，不能偷偷改需求消除失败。

## 3. 开发相关预制件与场景

使用已准备的 `workspace.json.godot_project`，必要时 `workspace_prepare`，保留未提交文件及同伴修改。读当前工具 schema 与 `WORLD-API.md` 后选最小合适写入方式：

- 已公开参数：`semantic_apply set_property/reset_property`，使用真实属性版本和定义/实例地址。
- 原生代码/场景/资源：编辑实际 `.gd/.tscn/.tres` 等文件，通过 `world_apply` 的 `submit_native_workspace` 提交；小型文本修改可按当前契约用 `put_source_file`。携带真实基线、environment、submit_path 和事务 ID。冲突时读取最新源并保留本地差异，不覆盖同伴变更。
- 新增/重构预制件：遵守 `WORLD-API.md` 的 “Prefab authoring and structure”，创建可独立编辑的真实 PackedScene，登记目录，并接入场景实例或实际生成逻辑；不要只创建未使用的资源卡片。
- 需要素材时读取同级 [game-assets](../game-assets/SKILL.md)，复用或获取适合的美术/音效/UI，保持实际依赖闭包与来源记录。仅下载不等于已集成。

混用参数/知识/素材工具与本地工程编辑时，每次中央写入后核对新 revision，再刷新或协调可编辑工程的基线，保留未提交差异；不要用旧副本覆盖刚保存的参数或依赖。

完整原生文件是唯一内容权威，`native_nodes` 是查询索引。保留未知节点/属性、ID、连接、资源与实例覆盖；定义普通修改由 PackedScene 继承，不逐实例升级。历史 flat/H2 工程按其当前契约处理，不擅自迁移。变更通过同一中央事务保存，不能另造一套 JSON 场景或测试专用玩法实现。

## 4. 同步描述、暴露属性和修改记录

真实行为实现后，更新受影响场景和预制件的用途、规则、关联和使用说明。原生 `@export` 属性自动可发现；用 `semantic_read` 核对后，通过 `semantic_apply update_design` 或同一原生目录提交补充 `design`。合并现有描述、`relations` 和 `exposed_properties`，不要用局部列表覆盖其他仍有效的条目。

只暴露对创作者有用、已经绑定实际行为的属性。记录名称、类型、默认值、单位、范围/步长、说明、是否实例可改；原生绑定使用真实 `node_id`、`property` 和必要的 `instance_ids`。不把描述中的新参数当作已实现功能，不暴露无意义的内部缓存。重置应移除原生覆盖，保留未来跟随默认值的行为。

按 [变更记录结构](references/change-record.md) 更新当前任务记录，包含动机、前后行为、对象、源码 revision、验证状态与遗留项。允许文件写入时保存到会话 `outputs/tasks/<run_id>/change-record.md` 并在当前任务回复中记录正文/路径；任务对话始终保留可读的变更与交付说明，不直接改任务数据库或伪造 task_write。

已落实且适合共享的结构/玩法决定，用 `knowledge_search/read` 找原条目，再按最新版本 `knowledge_write` 更新公共摘要；不复制私人会话或测试日志。知识写入也会推进源版本，之后重新核对基线；它不能代替任务内修改记录或真实源文件。规划模式不执行这些写入。

## 5. 验收与交付

执行选定的检查并按结果修复。源码保存后读回实际 revision、目录、引用和属性；若做技术验证，`game_validate` / `workspace_test` 使用已登记的固定 canonical 工程。`workspace_test` 检查固定输入，不能证明尚未提交的本地变更。实际启动统一走 `GameRuntime` + `standalone.tscn`，检查真实场景与代次，不能拿模型预览结果当作游戏通过。

Godot 使用 `workspace.json.engine.executable`，默认 headless、Dummy 音频和有限时长。必要的画面检查只用 `--wa-render` 后台模式及脚本输入，读取保存图片；不打开/激活 Godot、不注入桌面输入、不播放声音，渲染不可用时报告缺口，不回退普通窗口。音频导入/触发检查与听感验收分别表述，不把测试静音写入玩家源稿。

交付说明包含：做了什么、可定位的场景/预制件与关键属性、保存 revision/实际产物入口、每项检查的输入和结果、未测试或失败的具体行为、下一步确实需要用户处理的事项。报告已完成与尚未满足的需求，不能仅凭文件存在、一次构建或历史报告宣称玩法通过。

编辑 Play 是每窗口独立运行。多人需求需要实际权威/同步与控制证据；共享编辑不能算多人游戏。普通源保存不调用 `world_publish`，公开试玩发行和显式共享世界任务各需对应授权与真实回执；保留 `/goal` 持续执行，不增加自动验收/发布流程。
