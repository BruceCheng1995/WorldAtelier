# 用户体验 Case：从易到难

配套：[核心需求与进度](PRODUCT-EXPERIENCE.md)。本文件是体验目标，**本轮全部未执行**；不替代 [技术专项验收](CREATION-ACCEPTANCE.md)。

统一题材为“协作小岛”：地面、出生点、小屋、可开关的门。仅用于测试，不限定游戏类型，也不替代 [原验收指定的三个内容任务](../tests/creation/ACCEPTANCE-PLAN.md#7-三个最终真实任务)。

## 执行方式

- 用真实界面完成操作。协议测试、直接改库或预埋脚本不能代替用户完成；预置内容只能用于已明确允许的局部 case。
- 单项可从前序产物或注明来源的夹具开始；Case 03、04、18 必须真创作。夹具跑通不算从空游戏跑通。
- 双人 case 使用独立账号和浏览器登录上下文；Agent 必须真实执行。隔离测试数据，不清空日常演示工程。
- 每例记录：`版本 / 时间｜前置来源｜通过、失败、阻塞或未执行｜卡在哪一步｜截图 / 录屏｜必要的执行证据`。缺前置记阻塞，不跳过后写通过。
- 先给测试者任务目的，让其自行找入口；记录耗时、求助、误操作和对修改范围的判断。开发 Agent 操作通过后，“新人是否理解”仍需真人走查，不预设虚构的性能成绩。

## 一级：看得懂、改得动

### Case 01｜找到工作对象（R01、R03）

- **前置：**一个注明来源的样例游戏，含两个场景、一个未摆放的预制件。
- **操作：**进入分支 → 打开另一个场景 → 在视口选对象 → 从目录找到未摆放预制件 → 开关聊天抽屉。
- **通过：**能说清当前游戏、分支、场景与选中对象；树、视口、属性一致；关闭聊天后视口可用，原选中和草稿保留；对象 / 协作入口可找到。

### Case 02｜完成一次空间编辑（R03）

- **前置：**可编辑场景及一个有效模型文件。
- **操作：**通过界面导入模型 → 选中 → 移动到非零高度、旋转、分别缩放三轴 → 撤销 / 重做 → 再拖动并取消。
- **通过：**实际模型与数值一致；能绕看、聚焦；撤销一次只退一笔操作；取消回到拖动前；在聊天输入快捷键不会误动对象。重开后的保存另见 Case 16。

## 二级：从想法做出内容

### Case 03｜空游戏到两个场景（R01、R02）

- **前置：**新建空游戏，无预制好的任务成果。
- **操作：**新会话说“创建一个有地面和出生点的小岛场景” → 再说“新建一个室内测试场景，保留小岛” → 打开两个结果 → 退出后重进。
- **通过：**真实 Agent 产出两个可独立打开的场景；旧场景没被覆盖；能从对话找到结果；重进后资源和会话仍在。此例不宣称已可玩。

### Case 04｜做出可发现、可独立编辑的预制件（R02、R04）

- **前置：**Case 03 产物；所需执行器可用。
- **操作：**要求“通过 Blender 制作一块路牌美术预制件”和“制作带可开关门的小屋预制件” → 暂不摆放 → 从全部目录搜索两者 → 独立打开，再摆入场景。
- **通过：**有本次真实制作过程和产物；未摆放也能发现；模型可实际查看；美术、逻辑与预制件的关联可追溯；独立编辑不改主场景。门是否能玩由 Case 08 验。

### Case 05｜只改一个，或修改全部（R03、R04）

- **前置：**两个场景共三个同源小屋实例，其中一个已有颜色覆盖。
- **操作：**只把第一座改红 → 打开小屋定义修改门的默认参数 → 查看影响范围、确认更新 → 检查三个实例；把路牌嵌入小屋并移动整屋，再改其中一个实例的路牌；最后尝试删除被实例覆盖的内部节点。
- **通过：**用户在提交前知道谁会改变；单例修改不波及其他实例；定义更新按明确策略传播，原颜色覆盖保留；子物体跟随父级且实例可准确区分；无法沿用的覆盖有冲突提示和处理入口；编辑预览地面不会混入定义。

### Case 06｜“改这个，放这里”（R02、R06）

- **前置：**一个对象、两个会话。
- **操作：**对象加入指定会话；创建无模型锚点，移到 `(12.5, 3, -8.25)` 并附到同一会话 → 发送“在附件位置放一个入口” → 移动锚点、改名对象 → 查看旧消息与成果。
- **通过：**加入附件不自动执行；发送后真实 Agent 按附件落点；旧附件中的对象身份、所属分支、位置、当时版本不变，不能跟随最新选择；新位置需新附件。测试坐标不限定用户的创作范围。

### Case 07｜工作可以放下再继续（R05、R12）

- **前置：**A、B 同属一个项目；A 有两个私人会话。
- **操作：**A 在两会话分别留草稿 / 附件，其中一条发送目标 → 开关抽屉、切会话、重新登录 → 继续第二轮对话 → B 查看协作面板，再由 A 显式共享一个会话。
- **通过：**各会话上下文不串；未发送内容和历史可恢复；续聊接着原任务；B 默认看不到私人正文 / 附件 / 工具参数，共享后只看到获准内容，不能代 A 回复执行审批。

## 三级：实际试玩与共同编辑

### Case 08｜玩到刚刚做的内容（R08）

- **前置：**Case 04 生成的小屋已摆放；源稿有一处尚未进入可玩版本的新变化。
- **操作：**A. 直接点击 Play → 等待准备 → 在当前网页视口移动、碰撞、开关门 → 返回编辑；B. 独立一轮使用注明来源、会准备失败的候选 → 点击 Play → 查看失败并重试。
- **通过：**A 玩到本次目标版本和新逻辑，往返保留场景 / 预制件标签、选中、相机书签与会话；B 说明失败与目标版本，保留编辑上下文，可重试；不能悄悄玩旧版。两变体分别记录，只有模型画面不算通过。

### Case 09｜两个人和 Agent 改同一场景（R07）

- **前置：**A 邀请 B 以编辑者加入同一分支、同一场景。
- **操作：**A 移动小屋；B 同时旋转路牌；A 让 Agent 在路边加一盏灯 → 两人检查结果。
- **通过：**无需手动刷新，双方看到对方拖动预览和最终提交、Agent 新对象；不同对象的修改都保留；各自选中、相机和草稿互不抢占；协作状态对应真实用户。

### Case 10｜撞车与撤销不丢成果（R07）

- **前置：**A、B 同场景。
- **操作：**分别执行：A. 两人同时移动同一对象并处理冲突；B. B 改另一个对象后，A 撤销自己的上一笔；C. B 后改 A 刚改过的同一对象，A 再撤销；D. B 删除 A 正选中的对象。
- **通过：**A 冲突可见，自己的意图可保留 / 重做；B 撤销不撤掉 B 的修改；C 旧撤销遇到冲突，不能覆盖 B 的后改；D 明确提示删除，选择或附件不跳到另一个对象。每个变体重开后双方结果一致，分别记结果。

### Case 11｜我停下来检查，世界继续（R06、R09）

- **前置：**A、B 在同一在线世界试玩。
- **操作：**A 移动中进入个人检查、松开按键、绕看小屋；B 继续游玩并移动 / 删除相关对象 → A 批注并尝试编辑 → 返回实时。
- **通过：**只固定 A 的观察，B 继续；A 角色不延续旧移动输入；相机、拾取、附件和源稿编辑仍可用；后续修改有提示，旧观察不覆盖新内容；恢复到当前世界而非倒回暂停时，旧按键不重放。检查期间的动态位置不会自动变成初始布局。

### Case 12｜边玩边改，坏修改不毁现场（R10）

- **前置：**双人在玩；小屋门已打开，已有可辨认的玩家进度。
- **操作：**通过会话做一次兼容的门外观 / 参数修改并应用 → 继续操作 → 再提交一个注明来源、验证会失败的候选。
- **通过：**成功变更在当前运行中可见，既有进度按声明的兼容规则保留；失败保留最后可用内容和场景上下文，说明原因、影响和重试方式；正在编辑、已可玩、当前世界使用的版本能分清。不用重开后重玩冒充连续更新。

### Case 13｜Agent 的“完成”可信（R02、R10）

- **前置：**同一小屋关联“换外观”“实现开门”两个独立目标。
- **操作：**只完成外观任务 → 查看对象状态；再分别执行：A. 开门任务遇到可控工具失败并重试；B. 新目标中断，确认终止后发新目标；C. 触发一次真实输入 / 审批请求，由会话主人回复后继续。
- **通过：**外观完成不让开门任务一起完成；选中与维护状态可区分，每个目标可追踪；失败、等待回复、中断、待用户检验有明确状态；取消后旧运行不能继续修改；工具结束或已应用不自动证明门能开，需 Case 08 实测。变体分别记结果，未触发真实请求不能把 C 标通过。

## 四级：分支、异常与完整闭环

### Case 14｜分出去，也是一套完整工作台（R05、R11）

- **前置：**main 可编辑；A 有未发送草稿、附件和一个进行中的目标。
- **操作：**从明确版本分出“夜景” → 在分支创建两个会话并修改灯光、Play → B 留在 main 继续编辑 → A 来回切换；从个人检查旧版本再发起分支时查看来源选项。
- **通过：**main 与夜景均有同级入口和完整工具；各自内容 / 会话 / 世界不串；旧目标继续绑定 main；原草稿、附件保留；分出版本可辨认，“带上下文继续”须显式操作，不复制所有人的私人会话，也不默认搬入在线玩家进度。

### Case 15｜合回来，还能继续做（R11）

- **前置：**main 与夜景各有不同对象修改，另有一处同对象冲突；main 有正在游玩的用户。
- **操作：**比较夜景 → main → 查看影响并选冲突结果 → 合并 → 验证后应用 → 夜景再改一处并第二次合并；另试比较期间 main 被 B 修改。
- **通过：**用户确认前知道合入什么、冲突如何取舍；不冲突内容保留；目标已变时要求重新核对；源分支不消失，第二次不重复合入旧修改；合并本身不覆盖主干在线进度，应用是明确的后续动作。

### Case 16｜意外发生，还能继续（R03、R12）

- **前置：**有已保存编辑、未发送草稿和最后可用模型。以下变体独立执行、分别记结果。
- **操作：**A. 刷新 / 退出重进；B. 断网时尝试提交，恢复后重试；C. 用非法模型替换现有模型；D. 真实 Agent 执行中断开连接后恢复并核对状态。
- **通过：**A 已保存内容、会话与草稿可恢复；B 未确认修改不显示已保存，恢复后不重复；C 原模型和引用保留，失败可理解；D 不盲目重跑目标，未知状态明确且可继续核对。任何变体失败，整例不能标为全部通过。

### Case 17｜协作权限边界清楚（R05、R12）

- **前置：**A 为所有者，B 为编辑者，另有只读成员；B 持有编辑草稿和私人会话。
- **操作：**只读成员尝试修改 → A 将 B 降为只读 / 移出项目 → B 继续提交或发送目标 → A 查看公共协作信息。
- **通过：**角色权限能理解；失去权限时立即说明，旧页面 / 排队目标不能继续写入；不把失败提交显示为成功；公共维护状态不泄露 B 的私人对话，A 也不能因管理项目而直接代答 B 的私人执行请求。

### Case 18｜从空游戏完成一次共同创作（核心旅程串联）

- **前置：**两个独立真实账号、一个真实 Agent；全新空游戏，无预制任务成果。
- **操作：**邀请 → 对话创建场景和美术 / 逻辑预制件 → 双人摆放 → 当前视口开门试玩 → A 个人检查、精确批注，B 继续 → Agent 修改并现场复验 → 分支独立修改、比较合并 → 两人重新进入继续创作。
- **通过：**同一次旅程明确看到八项结果：①真实新场景；②美术 / 逻辑预制件可从全部目录独立打开；③双方修改可见；④同视口实际开门；⑤A 检查时 B 继续；⑥Agent 按固定附件修改且复验有效；⑦分支修改互不影响、合并结果正确；⑧重进保留内容与会话。无后台修数据或换预制演示跳过。每项分别记录；未完成就停在具体步骤。
- **范围：**此例验证流程能连起来。实例升级、私人共享、失败中断等仍按对应分项独立记录；本例通过不自动让 Case 01–17 或原专项验收通过。

## 五级：跨端能力（建议验证顺序，不改变需求范围）

### Case 19｜离线做完，回来共同编辑（R13）

- **前置：**下载指定分支、明确基础版本的原生 / 离线工作区。
- **操作：**离线改小屋并试玩获得进度；B 在线改路牌 → 回传内容、处理冲突 → 在 Web 查看、试玩并继续编辑。
- **通过：**双方内容保留；超出跨端支持范围时明确说明，不能静默丢字段；离线试玩进度不覆盖在线玩家进度；同版本在目标端的模型、布局和逻辑一致。

### Case 20｜切换客户端版本后接续（R13）

- **前置：**已有在线进度；一个明确要求更新客户端的候选版本。成功、准备失败分两次执行。
- **操作：**请求进入新版本 → 等待准备和交接 → 继续操作；另一轮让候选下载 / 加载失败。
- **通过：**用户知道要去哪里、当前在等什么；成功按目标规则接续状态与控制，不重放旧输入；失败保留可恢复状态；允许新运行实例与可见等待，不能宣传为原实例零等待热更新。
