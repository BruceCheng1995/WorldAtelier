# 打包性能研究 · 2026-09-09

结论：当前最值得先做的是复用已有包、修正工具链哈希缓存，再缩短逐资源运行检查。现有数据不支持优先扩大全局 worker 并发；单纯保存导入缓存的本例收益较小。本轮只做研究与隔离测量，未修改产品实现、发布记录或重启正式服务。

## 建议顺序

### 1. 让显式打包复用已经完成的 Play 包

`preparePlay()`（约 214 行）会复用既有 Web 导出；`create()`（225–249 行）只有 `request_id` 幂等，生成内容身份后仍直接入队。相同输入的两个入口目前只有单向复用。

建议抽出公共的匹配与复用逻辑：相同固定输入和平台产物存在且完整时，复用完成包；相同目标正在构建时合并请求。保持请求幂等、当前权限、各平台完整身份及产物哈希校验。多平台任务不能仅凭含 Web 的公共 `content_key` 判定所有目标都满足。

收益：本样本第二次操作可避免约 37 秒的完整重建，只支付查找、授权和产物校验。尚未实现，因此不声称点击后已秒开。构建完成与明确发布仍分开。

### 2. 修正工具链文件哈希缓存的反复清空

`fileIdentity()`（22–26 行）在缓存超过 40 项时整体清空；当前 Godot 应用包包含 80 个文件，另有模板。一次遍历已超过容量，后续每条命令的 `verifyToolchain()` 都会反复读文件，主二进制还有被重复计算的情况。

按当前算法独立复现：热轮每次重新哈希约 689.23 MiB，耗时 0.319–0.338 秒。仅在实验中将容量改为 256 后，热轮未重新读取文件字节，耗时 1.5–2.0 毫秒。此为算法微基准，未改正式代码。

建议按真实路径维护可失效的文件身份/LRU，而非达到小阈值就全部清空；沿用实际文件元数据检查及变化后重算哈希。构建前后保持工具链一致性验证。收益预期为多命令构建节省数秒，并减少主服务同步读文件；总流水线收益仍需实施后测量。

### 3. 缩短每次 Play/打包必须逐资源运行的路径

当前每次都把场景、预制件及历史兼容资源共 10 项分别启动一次 Godot。资源数量增加会继续线性放大这一成本。

优先讨论的方案：普通 Play/出包保留完整导入、编译错误检查与真实入口启动确认，将逐资源 180 迭代检查留在显式验证或 Agent 自选测试中。不要自动调度独立验证 Agent，也不要将全量检查搬到每次编辑后的自动后台任务。

该方案会改变默认检查覆盖范围：入口未用到的预制件运行故障可能延后发现，必须明确这一取舍。若要保持现有全量覆盖，可评估 2 个隔离检查进程的有限并行，但需独立保存目录、独立可写缓存、完整取消/超时处理；本轮没有测量该方案的并行收益。不要仅缩短帧数就宣称覆盖不变。

### 4. 再做导入缓存及导出引擎复用

保留按工具链、原始资源、导入设置和依赖确定的导入缓存，供独立工程复制使用。不能直接重用运行检查后可能被作者脚本修改的整个目录；未知原生文件、完整资源闭包和隔离边界继续保留。当前样本热导入只省约 0.4 秒，需与更大美术资源工程一起评估。

导出每次复制约 341 MiB 的 Godot 应用包，用于私有 `editor_data`。可研究文件系统克隆或可信只读引擎配合每任务私有数据目录，保持现有隔离语义；复制与首次启动的准确分摊需要新增计时。

更后续可研究固定 Web 引擎、只更新内容 PCK。Godot 4.6 官方支持 [`--export-pack`](https://docs.godotengine.org/en/4.6/tutorials/editor/command_line_tutorial.html)，但这不自动解决 Web HTML 的尺寸配置、运行身份、模板特性和 HTTP 适配。当前 WASM 是约 35.94 MiB 的现成模板，流程并没有每次编译 Godot 引擎；此方向主要减少重复复制、压缩和传输，不应包装成“免除引擎编译”。
