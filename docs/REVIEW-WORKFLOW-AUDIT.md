# 目标验收：必要性、依赖与简化建议

> 本文保留改造前的审计结论。2026-09-08 开发者要求取消人工验收后，现行流程已改为 [自动检查与 Inbox](./AUTOMATIC-VERIFICATION-INBOX.md)，实现与新验证记录见 [实施记录](./AUTOMATIC-VERIFICATION-REPORT.md)。下文对旧表单及其限制的描述不代表现行操作要求。

检查时间：2026-09-07，当前 WorldAtelier 工作区代码及 48910 真实工作台。本文是审查与方案，尚未实施产品调整。

**结论：应保留真实验证与可追溯结果，把日常创作中的正式人工验收降为可选。** 当前验收并不是保存、继续开发、合并、应用场景或 Play 的通行证；它主要是一套质量记录和协作状态显示。用户不需要为了继续开发先把所有目标、预制件或系统逐一验收。

有价值的是证明“改了什么、检查了什么、是否真的进入运行世界”；用户逐项填写条件、操作记录、选择报告和作出正式决定，是当前实现选择，可以简化。系统开发团队对平台本身的完整验证责任，也不应转成每位创作者的日常工作。

**这套逻辑从哪里来。** 原始创作主线是对话创建游戏、场景和预制件，多人共同编辑，在当前 Web 视口 Play。[原始 brief](/Users/chengzhi/Projects/WorldAtelier/docs/CREATION-WORKFLOW-BRIEF.md:7) 没有要求创作者对所有预制件逐项填表。

后来补充了必要的目标因果关系：例如“把门改个名字”不能被当作“实现交互开门”完成；Agent 结束、技术检查通过、场景已应用、目标体验达成需要分开记录。[目标语义](/Users/chengzhi/Projects/WorldAtelier/docs/CREATION-WORKSPACE.md:117)

独立验收模块随后把“有对应目标依据”具体化为固定目标、执行轮次、完整源版本、构建、世界代次，以及每条条件的人工观察证据和不可变决定。完整源版本保守失效、逐条人工证据、默认要求在线世界，均属于可以调整的实现策略。[模块规则](/Users/chengzhi/Projects/WorldAtelier/docs/handoffs/goal-review-HANDOFF.md:56)

需要区分三个层次：

| 层次 | 应由谁承担 | 必要的结果 |
| --- | --- | --- |
| WorldAtelier 平台交付验证 | 我们的开发与独立测试角色 | 证明真实 Agent、多人同世界、预制件独立编辑、Web Play、恢复与权限能够协同工作 |
| 日常创作目标的交付与反馈 | 系统自动检查为主，创作者表达意图和反馈 | 说明本次成果、验证范围、已知问题和体验是否符合意图 |
| 稳定版本的发布质量要求 | 项目配置的发布策略与负责人 | 固定候选版本、依赖和兼容性，完成相应回归及发布决定 |

[平台交付规范](/Users/chengzhi/Projects/WorldAtelier/docs/CREATION-ACCEPTANCE.md:5) 规定真实的独立验证角色；[架构](/Users/chengzhi/Projects/WorldAtelier/docs/ARCHITECTURE.md:82) 同时明确普通授权编辑自动推进，不为每次保存增加确认弹窗。架构中的 playable_head“验收要求”不是产品内 goal-review 的同义接口，不能从措辞推断代码依赖。

**它依赖哪些上游流程。** 当前完整成功路径是：目标存在且执行结束 → 固定当前分支源版本 → 取得属于该目标运行的同版本技术报告 → 匹配的场景应用 → 记录实际检查与证据 → 授权者提交本轮决定。

| 前提 | 当前约束 | 为什么会增加操作成本 |
| --- | --- | --- |
| 目标与执行 | 绑定会话主人、当前 run 和目标对象身份；最终通过要求 run 为 completed | 旧 run 失败后，即使别人已修好内容，仍需要续修成功轮次 |
| 源版本 | 必须固定整个 branch.head；后继协作版本需为原目标重新生成技术报告 | 无关场景改动也使旧报告不再适用当前轮次 |
| 技术报告 | 所选报告必须属于同一目标运行、源版本、构建且已结束 | 用户需要理解选择的文档、构建和报告 |
| 现场应用 | UI 强制 requires_application=true；证据采集还要求真实在线 Godot 世界 | 纯外观、名称等编辑也被带入完整世界流程 |
| 证据 | 每条条件需有检查结果和实际观察；可用一份记录覆盖多条，图片可选 | 写条件后还要重复选择结果、填写观察 |
| 权限 | 主人组织；其他验收者需共享会话、项目编辑权及本轮委派 | 不能把“找别人看看”当作无需设置的轻量协作 |

**实际存在的连带影响。**

1. **准备验收可能更新其他人的共享现场。** 当前源版本没有该目标的报告时，prepare 进入 technical('publish')。用户在“验证并应用”对话框确认后，实际验证并创建或更新所选场景的权威世界，向在线玩家发送场景和快照。这不是仅保存一份检查记录。界面已有说明和确认，但把它组合在验收入口中，仍使“检查成果”承担了共享现场变更。[入口](/Users/chengzhi/Projects/WorldAtelier/apps/creation-workspace/goal-workspace.js:133)、[场景广播](/Users/chengzhi/Projects/WorldAtelier/services/creation/worlds.mjs:184)
2. **无关协作改动也影响别人的验收状态。** facts 直接比较整个分支 head。A 验收蛇头之后，B 修改独立 UI 场景，也足以让 A 的结论变成历史适用，而非当前通过。历史决定保留，但当前状态退回。[失效判断](/Users/chengzhi/Projects/WorldAtelier/services/creation/goal-review.mjs:218)
3. **旧目标拖累整个对象状态。** 同对象所有目标必须当前 accepted 才是 delivered；任一旧目标未评价或已失效，对象就可能长期像尚未完工。它影响协作判断和呈现，没有实际阻止用户编辑。[聚合规则](/Users/chengzhi/Projects/WorldAtelier/apps/creation-workspace/collaboration-client.js:124)
4. **轻量编辑没有真正轻量的路径。** 底层账本支持不要求世界应用，当前 UI 却锁死为要求；当前实际采集接口仍只支持在线世界。不能把底层 boolean 支持描述成产品已经支持纯编辑验收。
5. **形式门槛与成果质量不总一致。** 后继版本允许为 failed/cancelled 旧运行复验，但 pass 仍只接受 completed。另一个协作者修复后的成果可能技术通过，仍须补一次成功执行才能完成正式流程。[复验资格](/Users/chengzhi/Projects/WorldAtelier/services/creation/goal-revalidation.mjs:3)、[通过门槛](/Users/chengzhi/Projects/WorldAtelier/services/creation/goal-review.mjs:263)
6. **记录增加保留成本。** 现有采集无垃圾回收；所有轮次和留存字节进入备份。反复验收会增加长期存储、恢复和维护工作。[保留策略](/Users/chengzhi/Projects/WorldAtelier/services/creation/review-capture.mjs:223)
7. **已应用状态不等于实时在线。** 面板应用状态读取持久化的世界记录；真正采集会额外核验当前服务内的在线 Godot 连接。界面显示“已应用”时，采集仍可能因世界离线或恢复代次变化而失败。

正常世界 sequence 增长本身不使证据失效；源/构建/世界代次或固定身份变化才可能影响其当前适用性。不能把“游戏继续运行”误说成必然要求重新验收。

**繁琐并不代表覆盖全面。** 现有通过判断检查的是用户填写的条件和所选报告，没有自动要求覆盖全部改动资源、所有 run.targets、所有预制件或依赖闭包。原始文件哈希证明字节与版本绑定，不会证明用户填写的观察是真的，也不会自动判断画面是否好看或游戏是否有趣。

现有通用 Godot 验证覆盖资源加载、碰撞、20 帧物理、行为/表现生命周期等，代码明确限定为隔离的初始化与生命周期验证，不是完整浏览器、GPU 或玩法验收。[验证范围](/Users/chengzhi/Projects/WorldAtelier/runtimes/model-preview/authority_worker.gd:209) 当前也未接入自动试玩并作出目标质量结论的专门 Agent。目标 Agent 自述测试成功与服务端独立验证应分别展示。

**建议采用的日常路径：对话创作 → 自动检查 → 成果卡 → 直接 Play 或继续反馈。**

| 变化类型 | 默认系统承担 | 用户通常需要做什么 |
| --- | --- | --- |
| 名称、颜色、模型及普通配置 | 引用/资源检查、必要的渲染预览、改动摘要；按实际影响补碰撞等检查 | 看成果；不满意就直接说怎么改 |
| 可验证交互和玩法 | 独立测试角色执行真实输入、状态断言、异常记录及可重放用例 | 判断行为是否符合意图，以及手感是否满意 |
| 多目标组成的阶段成果 | 汇总本阶段变更、自动结果、问题和代表场景 | 体验一次完整功能，不逐个签所有预制件 |
| 对外稳定发行 | 固定候选的回归、兼容与迁移检查，按项目渠道策略处理 | 必要时做一次版本级决定 |

结果卡应只先展示“本次做了什么、可以在哪里看/玩、自动检查结果、仍不确定什么、继续修改”。版本、构建、世界及证据引用由系统绑定，详情折叠。日常未反馈可以记为“未评价”，不等同于失败或仍在开发；也不能自动写成“用户已验收”。

对预制件，用“定义版本 + 依赖”的通用检查复用结果；场景实例的覆盖、空间碰撞和组合行为按实际影响另测。蛇头和蛇尾是否可加载、独立打开、材质引用完整，应由系统检查；移动、增长、计分、碰撞、重开由可重复玩法用例检查。用户主要看整体风格、控制手感和玩法是否符合期望。当前不具备这些全部自动检查，需要逐步接入，不能仅改文案声称完成。

**减少重复劳动的关键是缩小失效范围。** 当前交付投影已经比较目标内容指纹，[已有基础](/Users/chengzhi/Projects/WorldAtelier/services/creation/agent-runs.mjs:405) 可用于进一步设计。但真正复用证据需要包含预制件、脚本、共享逻辑和运行构建的依赖；仅对象哈希相同不足以证明玩法未受影响。证据记录原验证版本与适用范围，后续无关变更保留结论，相关变更自动复跑。无法证明不受影响时可以保守自动复跑，仍不默认让用户重新填表。

自动检查也有成本：应对连续小改动合并调度，先跑快速检查，取消过时的候选检查，并缓存范围相同的结果；不要每拖动一次对象都启动重型独立试玩。失败时在原目标给出具体问题与续修入口。独立测试角色使用隔离世界和真实输入，不能通过直接写预期状态或伪造 ACK 制造成功；这与用户个人检查应保持同一共享世界、只冻结自己的呈现是两种不同用途。

**建议实施顺序。**

1. **先减少用户手续。** 日常入口改为成果与反馈，正式验收放入可选阶段审查；未评价不使对象长期显示施工中。已有记录继续可读。版本/报告自动选择；阶段确认可合并多个目标。
2. **分开检查与共享现场更新。** 查看成果或创建审查不隐含 publish；需要更新现场时沿用清楚的应用动作和真实回执。已有授权的常规创作仍按项目规则自动推进。
3. **补真正的自动验证。** 先做资源、预制件独立打开和少量常见玩法用例，提供实际画面/输入回放与结果。机器检查、开发 Agent 自述和人工确认分别标记；受托正式决定仍遵守原权限，不把测试 Agent 自动设为人的代签者。
4. **改为按依赖增量验证。** 自动复用未受影响报告，续修只呈现差异和未通过项；让成果质量依据与某个历史 Agent 运行是否成功适当解耦，保留执行错误历史。

改动主要在 goal-workspace / goal-review 展示、collaboration-client 聚合、agent-runs 状态投影、验证编排和证据适用范围。源稿、版本并发控制、Godot 权威应用和会话权限无需推翻。历史验收、证据及备份格式先兼容保留，后续再独立讨论保留策略，避免通过清理历史来制造“没有待验收”的假象。

实施后的目标应能直接观察：普通小改动不需要手填验收表；同一预制件未变依赖时不重复验证通用部分；无关场景变更不制造人工重新验收；查看审查不改共享世界；关键功能有系统实际检查和明确覆盖范围；用户仍能直接反馈问题并追溯原成果。

**检查范围与证据边界。** 本轮完成文档溯源、工作台真实表单检查、服务端账本/采集/复验/执行/世界调用链、前端与 Godot 状态消费者、备份及研发交接依赖审计。独立角色新运行验收/采集/前端逻辑测试共 58/58 通过；这些测试使用真实 SQLite 和明确的 Godot/Agent/UI 替身，只证明规则实现，不证明贪吃蛇完整体验已通过。本轮未修改产品代码或重启服务。
