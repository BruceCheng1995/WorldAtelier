# 分支、发行、世界状态与跳转协议

状态：目标协议。已有本地服务实现，实际字段见 [实现契约](../packages/contracts/IMPLEMENTATION.md)，已执行范围见 [验收记录](ACCEPTANCE.md)。未实现的分布式部署和私有权限视图不由本地共享世界测试推定。

## 1. 核心数据对象

| 对象 | 关键字段与约束 |
| --- | --- |
| Project | 工程 ID、成员权限、默认分支、发布渠道、存储与任务配额 |
| Branch | 分支 ID、源码 head、可玩 head、默认世界、分叉来源；主干使用同一模型 |
| Release | 不可变 ID、source revision、依赖哈希、目标客户端/权威端/内容包、引擎/接口/协议/schema、验收记录与状态兼容策略 |
| Workspace | 协作者、base revision、局部修改、离线状态、上传批次；不会自动变为共享世界 |
| World | world ID、所属分支、实际 release、持久化状态域、权威 epoch、事件序号、运行/休眠/准备状态 |
| Checkpoint | world/lineage ID、release、schema、epoch、覆盖到的事件序号、状态哈希、持久化水位与导出可见范围 |
| ViewBaseline | 按权限裁剪的客户端状态、view epoch、view sequence、权限策略版本与不透明续传游标；服务器保存其对应的世界水位 |
| Checkout | 目标意图、解析后的固定 release、匹配产物、状态模式、失效时间；不含永久控制权 |
| SessionTransfer | transfer ID、旧/新会话、玩家、目标世界、阶段、版本约束、控制代次与失败恢复记录 |

`release` 不可变；分支 head 是可移动指针；在线状态由 `world + epoch + sequence` 标识。单个全局 `latest` 字符串不足以表达它们。

## 2. 解析、下载与进入

建议入口：`POST /projects/{project}/checkouts`，请求目标 branch/release、目标平台、当前客户端能力以及以下一种状态模式。

| 模式 | 用途 | 状态规则 |
| --- | --- | --- |
| `join-live` | 加入共享在线世界 | 选择匹配发行的 world，下载后获取可连续同步的基线与订阅 |
| `preview-frozen` | 固定版本复现/个人验证 | 固定 release 与 checkpoint，创建独立 world，不写原世界 |
| `offline` | 离线编辑和试玩 | 下载授权依赖、客户端及状态种子；本地运行属于独立状态域 |

一次解析得到客户端程序、内容包及状态兼容约束。客户端下载缺少的对象并校验哈希，不逐文件追逐不断变化的主干。状态种子和构建必须有明确的兼容关系，不能只看日期最新。

`POST /checkouts/{id}/prepare-join` 在程序准备后再次核对 room epoch、实际发行版本与权限。在线世界若已升级，返回补齐/重新解析要求，或继续进入明确标识的兼容固定版本；不能静默混版。预约有期限，不能让一个慢客户端下载无限阻止整个房间更新。

只有目标实际加载了对应版本、完成状态同步且获得有效控制权，才回报进入成功。下载完成、进程启动、Web 页面打开分别是更早的阶段。

### 已连接客户端遇到世界升级

世界升级也需要版本门禁。协调者声明候选 release、内容代次与计划生效边界；运行端报告实际准备和应用结果，不能用下载完成代替应用确认。在权威的有序记录中提交版本生效事件，并记录实际生效序号。

客户端命令携带世界 epoch、内容代次和控制代次。版本边界之后，尚未确认已应用匹配内容与状态的客户端进入待同步状态，其旧规则命令被拒绝；完成同步后才重新授予操作资格。单个掉线客户端不无限阻止全世界更新，也不能继续操作新规则世界。只有声明并验证了兼容策略的旧客户端可跨该边界继续操作。

## 3. 检查点与连续状态

完整世界检查点在一个一致的逻辑边界记录状态，覆盖世界事件序号 n，恢复端从 n+1 接续。按权限裁剪的客户端使用独立的 `view epoch + view sequence`：其基线覆盖视图序号 m，增量从 m+1 连续送达。无权看到的世界事件不占用该客户端的视图序号，不能把正常过滤误判成丢包，也不发送占位事件泄露隐藏活动。

服务器将视图游标映射到内部世界水位，并建立订阅与缓冲屏障，防止下载基线期间漏掉变化。权限范围或视图规则变化时增加 view epoch，重新核验权限并生成新基线；客户端丢弃旧代次缓存，不拼接两个权限视图。

内容升级事件也进入有序记录，携带版本及迁移信息，并投递给受影响的客户端视图。对应事件流中途缺号、检查点过期、事件尾已截断或 epoch 不匹配，重新取得基线，不能跳过缺口后宣称已同步。

客户端接收的基线可以是按权限裁剪的状态视图；完整可离线运行的世界导出需要额外的状态与资产授权。隐藏世界数据和其他人的私有信息不因“下载状态”一并开放。

跨进程恢复使用权威状态和已接受的状态变化，不假定相同输入重放能在不同平台复现相同 Godot 物理。关键奖励/任务写入确认应关联持久化水位；高频显示与位置同步是否持久化、崩溃最多损失多少进度，需由实现明确测量和规定。

## 4. 离线合并与发布

1. 下载工作区时固定基础提交 B、依赖清单和所用工具链。
2. 离线得到修改 L；重新联网后取得服务器当前源码 head R。
3. 比较 B/L/R 做三方合并。节点稳定 ID、层级、资源 UID 与引用进行语义校验；GLB/`.blend` 等二进制冲突需要选版本或重新制作，不假装自动合并。
4. 通过条件更新推进源码 head：基础已被他人改变时重新处理，不能盲目覆盖。
5. 对确定提交构建和独立验收；所有需要的对象上传完整后，才有资格更新对应渠道的 playable head。调度时记录发布意图代次与目标源码提交；发布时校验该意图仍有效、源码关系符合渠道规则，并以预期 playable head 和渠道代次做条件更新。后完成的旧构建只登记历史发行，不能覆盖新提交已发布的版本。回退和分支历史改写使用显式操作与新的发布意图，不能伪装成普通推进。构建失败不覆盖上一个可玩版本。
6. 需要进入在线世界时执行热更新或世界迁移流程；发布成功本身不是房间应用回执。

世界检查点只随显式 fork/import 操作产生来源关系。内容合并不自动合并运行进度。注释或独立参数可按类型研究实时协作算法，但不把 CRDT 当作任意脚本、场景与物理状态冲突的通用解法。

## 5. 控制权交接

建议状态机：`requested → downloading → preparing → synchronized → transferring → active`，准备阶段可进入 `failed/cancelled`；交接提交后的失败进入 `recovery-required`。

- 目标先准备，只读同步，不能提前替旧角色发送有效操作。
- 最终交接前，根据状态继承策略取得必要的最新玩家状态；同世界升级和跨世界跳转使用不同策略，不能照搬整份旧世界快照。
- 最终交接先在旧输入入口封口，记录最后已接受操作、关联状态结果和持久化水位 F；目标确认应用到该水位或完成已声明的跨世界继承映射后，才允许激活。不同世界的序号不能直接比较，迁移回执要记录来源水位及目标结果。角色操作包含奖励等关键副作用时，已确认结果必须计入 F。
- 中央协调者持久化交接阶段，确保旧控制代次已在实际输入入口失效，再授予新代次；这不是把两个世界的远程调用当作单个数据库事务。只在短交接阶段收口该角色输入，不在整个下载期间暂停世界。旧入口无法确认封口或失去有效租约时，先完成围栏隔离，不能同时放行两端。
- 权威宿主迁移在最终逻辑边界收口整个世界的写入，包括其他玩家、计时器和服务端行为；生成可持久化的最终水位，目标恢复并确认后才成为新权威。只停一个角色不能得到整个世界的最终检查点；这一步可能短暂停止世界推进。
- 撤销必须由实际接受输入和持久化的入口执行。每个 world 的权威写者也持有递增 epoch，网络分区中的旧进程即使仍存活，其旧 epoch 写入也必须被拒绝。
- 准备失败时，旧会话继续且旧工作区不被删除。提交后新端失败，查询持久化 transfer 状态；通过新代次重新接续或发起返回，不能重新启用失效的旧票据。
- 每个角色控制槽最多一个有效写入会话；账号可拥有多个只读观察端。新的编辑权限按目标分支重新验证，不随角色控制权自动继承。

所有交接、发布、上传完成及关键玩法命令带幂等 ID。超时不等于未提交，重试必须查询/复用原操作 ID。一个客户端确认不能替代所有协作者或整个房间的状态。

## 6. 权限、调度与可靠性

成员权限按项目、分支、世界和操作分别核验，下载票据与加入票据短期有效；客户端可校验发布来源及产物哈希。已有离线副本不能被服务器凭空收回，权限撤销作用于后续下载、上传和在线接入。

开发/构建进程使用隔离工作区和有限凭证；一个主协调角色管理开发范围，一条独立验收通道生成明确证据。热更新行为仍需遵守模块与副作用契约，同进程任意 GDScript 不是安全沙箱。

世界按需唤醒与休眠；活跃 lease、检查点、release 与未完成下载都是存储保留引用。调度器记录任务占用、超时、重试和实际结果；不把丢失执行器当作成功。

## 7. 必须通过的故障验收

| 场景 | 必须保持的不变量 |
| --- | --- |
| 下载中主干继续发布 | 客户端获得固定且兼容的一套产物，或明确重新解析；不混版 |
| 旧构建晚于新构建完成 | 过期发布意图只登记历史发行，不能倒退可玩指针 |
| 检查点下载时世界继续运行 | 事件尾连续；缺口触发重同步；不能用旧进度覆盖世界 |
| 隐藏事件或权限视图改变 | 过滤不制造假丢包；新视图重新建立基线，不拼接旧权限缓存 |
| 离线两人改同一场景 | 冲突可定位，本地内容不丢失；可玩版本不被未验收源码取代 |
| 目标启动失败 | 交接前旧会话继续；没有假进入回执 |
| 交接提交后断网/重试 | 最多一个有效控制代次，查询原操作恢复；不复制角色或重复奖励 |
| 最终交接时仍有输入或定时事件 | 封口水位包含已确认结果；目标达到对应水位后才激活 |
| 权威进程网络分区 | 新权威生效后旧 epoch 的输入/持久化被拒绝 |
| 世界更新时旧客户端仍在线 | 按实际版本生效边界限制命令；未就绪端进入待同步状态 |
| 原生/Web 构建不匹配 | 平台明确不可用或要求匹配版本；不能退成静态预览声称可玩 |
| 合并源码分支 | 实验世界背包、任务、怪物状态不自动进入主干世界 |
| 清理存储和休眠世界 | 被引用版本可下载、检查点可恢复；验证真实恢复，而非只看备份文件存在 |

这些是验收要求；实际执行结果、所用运行时与尚未覆盖的边界记录在 [验收记录](ACCEPTANCE.md) 和 [独立测试说明](../tests/e2e/README.md)。
